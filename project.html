GT Movies Store

A Django web application for browsing movies, writing reviews, and placing orders. Built from the ground up and deployed to the cloud.

Open the live application

Overview

The GT Movies Store is a full-stack web application built with Python and Django 5. A visitor can read about the store, browse the movie catalog, and search it by title. After registering an account and logging in, that visitor can write reviews on any movie, edit or delete their own reviews, report reviews written by others, add movies to a shopping cart in whatever quantity they choose, purchase the contents of that cart, and look back over their past orders. Administrators use the Django admin panel to manage users, movies, reviews, and orders.

The application is organized into four Django apps, each responsible for one area of the site. The home app serves the landing and about pages. The movies app owns the movie catalog, the search, the detail pages, and the entire review system. The accounts app handles registration, login, logout, and the order history page. The cart app manages the shopping cart, which lives in the user's session, and turns a cart into a saved order at purchase time.

Data is modeled with four classes. Movie holds a name, price, description, and poster image. Review links a comment to both a movie and the user who wrote it, and carries a flag for whether it has been reported. Order records a purchase total and its owner, and Item records one movie, price, and quantity inside that order. Django's built-in User model handles accounts, which means password hashing and session security are handled by code that has been tested far more thoroughly than anything I would write myself.

Administration

The Django admin panel at /admin gives an administrator full create, read, update, and delete access to users, movies, reviews, and orders. I customized it in two places. The movie list is sorted by name and searchable by title, and the review list displays the reported flag as a column with a filter beside it, so an administrator can pull up every reported review in one click and decide whether to delete it or clear the flag.

Responsive interface

The layout is built on Bootstrap's grid system with a viewport meta tag, so the navigation collapses and the movie cards reflow into a single column on a narrow screen. The application is served over HTTPS from PythonAnywhere and works in any modern desktop or mobile browser.

Process

How I approached the work

I worked through the project incrementally rather than trying to design the whole application up front. Each stage added one complete, working feature: first the page structure and base template, then the movie model and catalog, then the database layer, then authentication, then reviews, then the cart and orders, and finally deployment. The advantage of that order is that the application is runnable at the end of every stage, so when something breaks, the cause is almost always in the small amount of code I just wrote rather than hidden somewhere in a large untested pile.

I leaned on the framework's conventions rather than fighting them. Django has strong opinions about where models, views, URLs, and templates belong, and following those conventions meant that features I had not written yet, like the admin panel, largely worked as soon as a model existed. The one place I designed something myself was user story 21, the review reporting feature, which was not covered by any of the course material.

Designing the reporting feature

The requirement was that a user can report an inappropriate review and that the review is removed from the page going forward. My first instinct was to delete the review outright, but I decided against it. Deleting is irreversible, and it would let any user erase anyone else's review with a single click with no record of what happened. Instead I added a boolean reported field to the Review model, defaulting to false. Reporting sets that flag, and the movie detail view filters reported reviews out of what it displays. The review disappears from the page exactly as the story requires, but it is still in the database, visible to an administrator through the admin panel where the reported flag is both a column and a filter. That turned one requirement into something that also strengthened the administrator stories.

Problems I ran into

Switching database engines. The course material walks through moving from SQLite to MySQL using XAMPP. On macOS this was less straightforward than the Windows screenshots suggested. The XAMPP control panel on macOS has no Admin button, so reaching phpMyAdmin meant navigating to localhost/phpmyadmin directly. More subtly, setting the database host to localhost failed with a socket error, because on macOS that value makes the driver look for a Unix socket file that XAMPP does not create where the driver expects it. Changing the host to 127.0.0.1 forces a normal TCP connection on port 3306 and resolved it. That is the kind of problem where the error message names a file path that does not obviously connect to the setting that caused it.

Deployment failing on the database configuration. After pushing to GitHub and cloning onto PythonAnywhere, the deployed site returned a generic error page. The error log gave the real answer immediately: Django could not load the MySQL driver. My settings file still pointed at a MySQL database on localhost, which made sense on my own machine where XAMPP was running, but on the hosting server there was no XAMPP, no MySQL server, and no driver installed. The fix was to point the deployed copy back at SQLite. The wider lesson was that a deployment environment is not a copy of a development machine, and configuration that assumes local services will fail the moment the code leaves that machine.

Static files not being served. Once the site loaded, it appeared with no styling, no logo, and no banner image. Django's development server serves static files automatically while debugging, but a production web server does not, and it will only serve files from directories it has been explicitly told about. Setting a STATIC_ROOT, running collectstatic to gather every static file into one directory, and registering that directory as a static file mapping resolved it.

Working out of order. At one point I started adding the accounts app before finishing the database chapter, which left the project in a state where the URL configuration referenced a file that did not exist yet, and the server refused to start. Sorting that out took reading the traceback carefully enough to see that the error was about a missing module rather than about my code being wrong. It made me more careful about finishing one unit of work before starting the next.

How I handled questions

My first move on any error was to read the traceback from the bottom up. Python prints the actual exception last, and the lines above it are the path that led there. For deployment problems the equivalent was the server error log, which is where the MySQL driver failure was spelled out in plain language while the browser was showing nothing but a generic apology. When the framework behavior itself was unclear, the Django documentation was more useful than searching, because it explains why a setting exists rather than just what to type. For the reporting feature, where there was no reference to follow, I looked at how the existing edit and delete review features were structured and matched their shape, so the new code reads like the rest of the application rather than like a bolt-on.

What I would do differently

I would separate configuration that differs between my machine and the server from the start, instead of discovering the difference at deployment time. I would also write the review reporting feature with a form submission rather than a plain link, since a link means the action happens on any visit to that address, which is fine for a class project but is not how a destructive action should work in general.
